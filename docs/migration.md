# Данные портала и их перенос

## Что такое seed_lessons

[`seed_lessons`](../app/knowledge/management/commands/seed_lessons.py) — команда
приложения Django для первоначального заполнения базы. В её Python-файле
сохранены четыре подготовленные статьи: о создании инфраструктуры, общем
хранилище, балансировке и отказоустойчивом приложении из ДЗ01–ДЗ04.
Каждая содержит номер урока, адрес страницы (`slug`), заголовок, краткое
описание и основной текст. Новые статьи сразу помечаются опубликованными.

Команда ищет статью по `slug`. Если её нет, создаёт запись; если она уже есть,
оставляет содержимое без изменений. Поэтому повторный запуск не перезаписывает
редакторские правки. Таблицы команда не создаёт и пользователей не добавляет.

Данные являются восстановленным начальным содержимым портала из исходников ДЗ04.
Исторического дампа работающего портала нет: внесённые в него позднее изменения
и загруженные файлы таким способом не восстанавливаются.

## Реализованный порядок

Перенос автоматически выполняет [migration.py](../scripts/remote/migration.py)
при настройке ВМ приложения; вручную запускать `seed_lessons` не требуется.

1. На этой ВМ создаётся отдельная временная PostgreSQL 16. Она слушает только
   `127.0.0.1:55432` и не занимает порт подключения к кластеру.
2. Создаются роль и база `otus`. Django `migrate` создаёт таблицы приложения
   и служебные таблицы пользователей, разрешений и миграций.
3. Django `seed_lessons` добавляет четыре статьи. Отдельная команда создаёт
   неактивного пользователя `migration-proof`, который служит проверкой переноса
   пользовательских данных и не предназначен для входа на сайт.
4. `pg_dump` сохраняет схему и данные в архив формата custom (`-Fc`).
5. Через HAProxy на `127.0.0.1:5432` создаются роль и база в кластере.
   `pg_restore` загружает архив в текущий ведущий PostgreSQL.
6. Проверка сравнивает исходные и целевые статьи по всем полям: `id`, `title`,
   `slug`, `lesson`, `summary`, `body`, `image`, `published`, `updated_at`.
   Дополнительно подтверждает наличие неактивного пользователя и запись
   на ведущий узел, а не на реплику.
7. Сохраняется `/opt/otus-dz06/migration-result.json`; после успешной проверки
   файл дампа удаляется. Временная PostgreSQL останавливается в блоке `finally`,
   включая завершение с ошибкой. Её каталог данных остаётся на диске ВМ до удаления ВМ.

При наличии отчёта завершённого переноса повторная настройка пропускает его,
сохраняя существующие записи. Это маркер выполненной операции; последующую
работоспособность и сохранность данных проверяют команды `verify` и `failover`.

Архив переносит схему и данные одной базы. Облачные настройки, PostgreSQL-роли
и файлы `media` в него не входят; роли создаёт сценарий, файлы находятся на ВМ
приложения. В данном наборе проверяется содержимое полей статей, включая имя
файла в поле `image`, а не перенос внешних изображений.

Подтверждения переноса включены в раздел `migration` отчётов
[первичной проверки](verification.json) и [восстановления](recovery-result.json).
