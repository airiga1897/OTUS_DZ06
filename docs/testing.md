# Проверки ДЗ06

Команды выполняются локально в PowerShell из корня репозитория после подготовки
окружения по [README](../README.md). Для облачных проверок требуется работающий
стенд и загруженная авторизация Selectel.

## Цикл основных команд

Последовательность для проверки: `deploy → verify → destroy`.
`destroy` выполняется и при ошибке предыдущей команды.
В [отчёте цикла](command-cycle-result.json) зафиксировано выполнение
всех трёх этапов в Selectel `ru-7a`. `deploy` создал кластер и портал;
`verify` проверил приложение, автоматическое переключение с db1 на db2,
сохранность данных и восстановление трёх работающих узлов.
`destroy` удалил стенд. [Аудит удаления](cleanup-result.json) подтверждает отсутствие ресурсов.
После сетевого тайм-аута API-аудита команда `destroy` выполнена повторно;
в отчёте сохранены коды завершения обоих вызовов. Итоговая очистка подтверждена.
[Проверка пулов](pool-cleanup-result.json) также подтверждает отсутствие именованных
ресурсов ДЗ06 в `ru-7` и `ru-9`.

## Подтверждённые испытания кластера

Отчёты ниже подтверждают проверки основными командами и дополнительные
испытания повторного развёртывания и двух последовательных фейловеров.
Основной цикл выполнен в `ru-7a`; отдельные отчёты повторного развёртывания
и двух фейловеров относятся к `ru-9a`.

| Команда | Проверяемое поведение | Подтверждённый результат |
| --- | --- | --- |
| `scripts/lab.py verify` | Роли, запись через HAProxy, портал, отказ лидера и восстановление | [Первичная проверка](verification.json), [восстановление](recovery-result.json) |
| `scripts/lab.py failover` | Смена лидера после выключения ВМ, запись и восстановление узла | [Два фейловера](failover-runs.json), [восстановление](recovery-result.json) |
| Повторный `scripts/lab.py deploy` | Сохранение UUID ресурсов и существующих записей | [Повторное развёртывание](redeployment-result.json) |
| `scripts/lab.py destroy` | Удаление ресурсов ДЗ06 и отсутствие остатков | [Облачный аудит](cleanup-result.json) |

Команды запускаются через `.\.tools\venv\Scripts\python.exe`, как в README.
Успех обозначается завершением без ошибки и соответствующими JSON-отчётами.
Проверки записывают новые строки в БД. `failover` временно выключает одну ВМ БД;
`destroy` удаляет весь стенд и его данные.

Команда `scripts/lab.py test` выполняет полный цикл:

1. Развёртывание Terraform и настройку серверов.
2. Первый фейловер: новую запись до выключения лидера, выбор нового primary,
   проверку сохранённой записи, новую запись после переключения и чтение через портал.
3. Возврат выключенного узла и чтение записей с каждого узла кластера.
4. Повторное развёртывание без изменения UUID ресурсов и повторного переноса БД.
5. Чтение записей первого испытания после повторной настройки.
6. Второй фейловер с отдельным run_id и новыми записями.
7. Удаление ресурсов ДЗ06 в finally и проверку пустого state и облачного инвентаря.

Каждая проверочная запись создаётся обычным INSERT RETURNING, фиксируется
транзакцией и читается через новое соединение. Проверяются ID, slug и body.
При проверке портала содержимое страницы сравнивается с созданной записью.
После возврата узла проверяются данные всех трёх PostgreSQL.

Результаты:

- [redeployment-result.json](redeployment-result.json) — сохранение ресурсов и данных после повторной настройки.
- [failover-runs.json](failover-runs.json) — оба фейловера, роли узлов и отдельные проверочные записи.
- [verification.json](verification.json), [failover-result.json](failover-result.json), [recovery-result.json](recovery-result.json) — последнее испытание.
- [cleanup-result.json](cleanup-result.json) — отсутствие ресурсов ДЗ06 после удаления.

Локальные проверки защиты от ошибочного удаления:

```powershell
.\.tools\venv\Scripts\python.exe scripts/test_lifecycle.py
```

Они проверяют сохранение существующего стенда при ошибке повторного deploy,
очистку частично созданного стенда при ошибке первого deploy и обязательную
очистку тестового цикла. Дополнительно проверяется использование ранее
подтверждённого SSH-ключа для того же UUID и обязательная проверка нового ключа
через API при изменении UUID. Облачные ресурсы в этих локальных проверках не создаются.
Дополнительный тест проверяет обязательную политику `anti-affinity` и отклонение
размещения двух узлов на одном хосте. Фактическое размещение в Selectel
подтверждено [облачным отчётом](placement-result.json).
Также проверяется повтор API-запроса чтения после тайм-аута и отсутствие
автоматического повтора команды управления питанием ВМ.
