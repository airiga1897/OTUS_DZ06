# ДЗ06 — PostgreSQL с Patroni в Selectel

19 октября 2026 выполнен полный облачный цикл: развёртывание, перенос БД,
проверка портала, выключение лидера, автоматический фейловер и возврат узла.
После испытания стенд удалён; фактическое завершение очистки отражено
в [cleanup-result.json](docs/cleanup-result.json).

Проверенные версии: PostgreSQL 16.15, Patroni 4.1.3, etcd 3.4.30.

9,84 с — время одного наблюдения, включающее ожидание Nova SHUTOFF и проверки;

Отчёты: [до отказа](docs/verification.json), [фейловер](docs/failover-result.json),

Три ВМ db1–db3 содержат PostgreSQL 16, Patroni и трёхчленный etcd.
Patroni использует etcd v3 API, автоматически выбирает лидера и управляет
репликацией. HAProxy на четвёртой ВМ проверяет REST `/primary` и направляет
подключения Django на текущий primary через неизменный адрес 127.0.0.1:5432.
На этой же ВМ работают Nginx и Django/uWSGI из ДЗ04.

| Роль | ВМ | vCPU/RAM на ВМ | SSD на ВМ |
|---|---:|---|---:|
| PostgreSQL + Patroni + etcd | 3 | 2 / 4 ГиБ | 20 ГБ |
| Django + uWSGI + Nginx + HAProxy | 1 | 1 / 2 ГиБ | 20 ГБ |

Итого 7 vCPU, 14 ГиБ RAM, 80 ГБ SSD, 1 floating IPv4. Пул ru-9,
зона ru-9a, сеть 10.66.0.0/24, имена otus-dz06. ДЗ05 использует другие
ресурсы, сеть и state. Учётная запись оператора может быть общей;
её пароль не передаётся ВМ. SSH-ключ и прикладные пароли создаются для ДЗ06.

## Требования и подготовка

Установить Terraform >=1.6,<2, Python и зависимости requirements-local.txt
в отдельный venv. На рабочем месте доступны инструменты ДЗ04;
скрипт также принимает OTUS_TERRAFORM с путём собственного Terraform.
Путь к Python в командах ниже соответствует проверяемому рабочему месту.
Для независимого клона создать .tools/venv и подставить его интерпретатор.

Оператор должен иметь доступ к Nova, Cinder, Neutron проекта Selectel OTUS.
Задать OS_* переменные или OTUS_SELECTEL_AUTH — путь к локальному JSON
с auth_url, project_id, region, domain_name, username, password.
JSON и ключи хранить локально, не публиковать. Поддерживаемый проект
фиксирован защитной проверкой в scripts/lab.py; для другого проекта
необходимо явно адаптировать этот контракт.

```powershell
cd D:\Projects\Codex\OTUS\OTUS_DZ06
. .\scripts\env.ps1
..\OTUS_DZ04\.tools\venv\Scripts\python.exe scripts/lab.py prepare
```

env.ps1 запрашивает номер аккаунта и пароль оператора скрытым вводом;
пароль сохраняется только в окружении сессии. Альтернатива — задать
OTUS_SELECTEL_AUTH с путём к уже существующему локальному operator.json.

prepare проверяет свободные общие квоты, разрешает текущие image/flavors,
создаёт собственные ключ и пароли, tfvars и выполняет init/validate.
Вызов не создаёт платные ресурсы. Перед каждым deploy/test квоты проверяются снова.
При раздельной маршрутизации VPN адрес HTTPS-сервиса определения IP может
отличаться от источника прямого SSH. В admin_cidrs локального tfvars нужно
указать реальные адреса оператора /32 для обоих маршрутов. prepare сохраняет
ранее настроенные /32; автоматическое определение HTTPS-IP не заменяет
проверку маршрута SSH. Открывать 0.0.0.0/0 не требуется.
При первом запуске временный HTTP route probe на самой ВМ возвращает адрес
источника прямого соединения и HMAC ответа с одноразовым nonce. Скрипт проверяет
ответ ключом конкретного стенда и при необходимости создаёт дополнительное
правило SSH для этого /32 через проверенный Terraform-план. Это учитывает
раздельную маршрутизацию VPN. Перед установкой Nginx временная служба отключается.

## Команды для проверяющего

Развёртывание (при успехе стенд остаётся для проверки):

```powershell
..\OTUS_DZ04\.tools\venv\Scripts\python.exe scripts/lab.py deploy
```

Проверка SQL, портала, переноса данных:

```powershell
..\OTUS_DZ04\.tools\venv\Scripts\python.exe scripts/lab.py verify
```

Отказное испытание с выключением текущего лидера через Nova и его восстановлением:

```powershell
..\OTUS_DZ04\.tools\venv\Scripts\python.exe scripts/lab.py failover
```

Удаление только ресурсов собственного Terraform state:

```powershell
..\OTUS_DZ04\.tools\venv\Scripts\python.exe scripts/lab.py cleanup
```

Автоматический тестовый цикл для разработки:

```powershell
..\OTUS_DZ04\.tools\venv\Scripts\python.exe scripts/lab.py test
```

test всегда вызывает cleanup в finally, включая неудачное создание и настройку.
deploy тоже очищает частично созданный стенд при ошибке. После cleanup
проверяются state, именованные ресурсы через API и отсутствие собственного
floating IP по UUID, сохранённому из state до удаления.
При аварийном прекращении процесса/потере питания finally не гарантируется:
после восстановления запустить cleanup вручную. Логи остаются в .local/runs.

## Перенос базы портала

Исторический дамп ДЗ04 не найден, облачный стенд удалён. Исходные четыре статьи
восстанавливаются командой seed_lessons в настоящей одиночной PostgreSQL 16
на ВМ приложения (временный порт 55432). Затем pg_dump -Fc и pg_restore
переносят схему и данные в Patroni через HAProxy. Сравниваются все поля
статей, включая PK и timestamps, и сохранение тестового неактивного пользователя.
После переноса временная PostgreSQL останавливается, дамп удаляется с ВМ.
Это перенос реконструированной БД, а не исторического production-дампа.
Исходные статьи не имеют media; файлы, если появятся, нужно резервировать
и переносить отдельно от SQL. Media текущего стенда хранится на ВМ приложения.

## Приёмка и ограничения

Проверка определяет текущего лидера по API Patroni. До отказа фиксируется
запись; после подтверждённого Nova SHUTOFF проверяются новый лидер, сохранённая
запись, новая SQL-запись, HTTP index/detail/readiness через тот же HAProxy.
После возврата узла ожидаются три running и наличие записей на каждом узле.
Результаты: docs/verification.json, failover-result.json, recovery-result.json,
cleanup-result.json после фактического прогона.

Включены synchronous_mode и synchronous_mode_strict с одной синхронной репликой.
Потеря доступных синхронных реплик может блокировать запись. Один пул и одна зона
не защищают от отказа ЦОД. Приложение, HAProxy и media имеют единственную ВМ.
Watchdog выключен: испытания выключения ВМ не доказывают безопасность любых
сетевых разделений и зависаний; промышленный вариант требует проработки fencing,
watchdog, TLS, резервных копий и резервирования входа. etcd/Patroni/PostgreSQL
доступны только в изолированной приватной сети, публичен HTTP портала и SSH
на TCP/443 с IPv4 /32 оператора; внутренний SSH — TCP/22.
Вход admin по HTTP выполнять только через SSH-туннель.
Незавершённые записи автоматически не повторяются; клиент при сбое получает ошибку.
